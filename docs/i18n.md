## For Developers

### Translation System Architecture

The I18N system uses **per-language YAML files** to maintain translations and a Python script to generate C++ code:

```
lib/I18n/
├── translations/                # One YAML file per language
│   ├── english.yaml
│   ├── spanish.yaml
│   ├── french.yaml
│   └── ...
├── I18n.h
├── I18n.cpp
├── I18nKeys.h                   # Enums (auto-generated)
├── I18nStrings.h                # String array declarations (auto-generated)
└── I18nStrings.cpp              # String array definitions (auto-generated)

scripts/
└── gen_i18n.py                  # Code generator script
```

**Key principle:** All translations are managed in the YAML files under `lib/I18n/translations/`. The Python script generates the necessary C++ code automatically.

The three generated files are `.gitignore`d — commit the YAML only. The generator runs as a
PlatformIO `pre:` script (`extra_scripts` in `platformio.ini`), so a normal `pio run` regenerates
them; run it by hand when you want to check your work without a firmware build.

---

### YAML File Format

Each language has its own file in `lib/I18n/translations/` (e.g. `spanish.yaml`).

A file looks like this:

```yaml
_language_name: "Español"
_language_code: "ES"
_order: "1"
_bcp47: "es"

STR_CROSSPOINT: "CrossPoint"
STR_BOOTING: "Iniciando..."
STR_BROWSE_FILES: "Explorador de archivos"
```

**Metadata keys** (prefixed with `_`):
- `_language_name` — Native display name shown to the user (e.g. "Français")
- `_language_code` — C++ enum name (e.g. "FR"). Please use the [ISO Code](https://en.wikipedia.org/wiki/List_of_ISO_639_language_codes) of the language. Must be a valid C++ identifier.
- `_order` — Optional historical metadata. Still validated for uniqueness when present, but no longer used to compute the `Language` enum order (see `_bcp47` below).
- `_bcp47` — [BCP 47](https://www.rfc-editor.org/rfc/rfc5646) language tag (e.g. `"pt-PT"`, `"ca-valencia"`). Must be unique. Controls the position in the `Language` enum and the visible Settings menu order (English is always first, then the rest sorted alphabetically by this tag). Persisted user language preferences are stored by `_language_code` string, not by the enum ordinal, so changing `_bcp47` (and thus the enum/menu order) does not reset anyone's saved language.

**Rules:**
- Use UTF-8 encoding
- Every line must follow the format: `KEY: "value"`
- Keys must be valid C++ identifiers (uppercase, starts with STR_)
- Keys must be unique within a file
- String values must be quoted
- Use `\n` for newlines, `\\` for literal backslashes, `\"` for literal quotes inside values

### What the generator enforces

`scripts/gen_i18n.py` is the only thing that validates the translation set, and it fails the build
rather than emitting broken tables:

- **English must exist.** Exactly one file must carry `_language_code: "EN"`; it supplies the
  master key list and the order of the `StrId` enum.
- **`_bcp47` is required and must be unique**, and so must `_order` where present (`_order` itself
  is optional). Duplicates are a hard error, because a non-deterministic language order would
  shuffle the enum.
- **Keys must be valid C++ identifiers**, checked against the English file.
- **A key used in code but missing from `english.yaml` fails the build.** The generator scans
  `src/` and `lib/` for `STR_*` references and exits non-zero with a `CRITICAL` list of the missing
  keys — this is why a typo in `tr(STR_…)` surfaces at build time rather than as blank text on the
  device.
- **Missing keys in a non-English file fall back to English** silently; pass `--verbose` to see the
  per-key `INFO` lines, and the per-language summary table always reports the fallback count.
- **Keys present in a translation but not in English are ignored**, and reported under `--verbose`.

Two size-related behaviors are worth knowing:

- **Identical strings are shared.** Each language gets a flat UTF-8 blob plus a 16-bit offset
  table. A non-English entry whose text matches English is not stored again — its offset sets bit
  15 (`0x8000`) to mean "read from the English blob". Keeping a brand name like `STR_CROSSPOINT`
  untranslated therefore costs nothing but the two offset bytes. Because offsets are 15-bit, a
  single language's blob may not exceed 32767 bytes; the generator raises if one does.
- **Unused keys are stripped from firmware builds.** Every run reports keys that no source file
  references. When PlatformIO imports the script as a `pre:` hook it calls it with
  `strip_unused=True`, so those keys never reach the device tables; a manual run keeps them unless
  you pass `--strip-unused` yourself.

```bash
python3 scripts/gen_i18n.py lib/I18n/translations lib/I18n/ --verbose
python3 scripts/gen_i18n.py lib/I18n/translations lib/I18n/ --strip-unused
```

### Adding New Strings

To add a new translatable string:

#### 1. Edit the English YAML file

Add the key to `lib/I18n/translations/english.yaml`:

```yaml
STR_MY_NEW_STRING: "My New String"
```

Then add translations in each language file. If a key is missing from a
language file, the generator automatically uses the English text as a
fallback (add `--verbose` to see which keys fell back).

#### 2. Run the generator script

```bash
python3 scripts/gen_i18n.py lib/I18n/translations lib/I18n/
```

This automatically:
- Fills missing translations from English
- Updates the `StrId` enum in `I18nKeys.h`
- Regenerates all language arrays in `I18nStrings.cpp`
- Fails with a `CRITICAL` error if your new `STR_` key is referenced in code but absent from
  `english.yaml`

#### 3. Use in code

```cpp
#include <CrossPointSettings.h>
#include <I18n.h>
#include <Logging.h>

// Using the tr() macro (recommended)
renderer.drawText(font, x, y, tr(STR_MY_NEW_STRING));

// Using I18N.get() directly
const char* text = I18N.get(StrId::STR_MY_NEW_STRING);
```

**That's it!** No manual array synchronization needed.

### Adding a New Language

To add support for a new language (e.g., Greek):

#### 1. Create a new YAML file

Create `lib/I18n/translations/greek.yaml`:

```yaml
_language_name: "Ελληνικά"
_language_code: "EL"
_order: "36"
_bcp47: "el"

STR_CROSSPOINT: "CrossPoint"
STR_BOOTING: "ΕΚΚΙΝΗΣΗ"
```

Pick a `_bcp47` tag no other file uses — the generator refuses duplicates. `_order` is optional, but
if you set one it must be unique too. The new language slots into the enum and the Settings menu by
its `_bcp47` tag, so adding one renumbers the ordinals of every language after it; that is safe,
because `settings.json` persists the `_language_code` string rather than the ordinal.

You only need to include the strings you have translations for. Missing
keys will fall back to English automatically.

#### 2. Run the generator

```bash
python3 scripts/gen_i18n.py lib/I18n/translations lib/I18n/
```

This automatically updates all necessary code.


### UTF-8 Encoding

The YAML files use UTF-8 encoding. Special characters are automatically converted to C++ UTF-8 hex sequences by the generator.

### I18N API Reference

```cpp
// === Convenience Macros (Recommended) ===

// tr(id) - Get translated string without StrId:: prefix
const char* text = tr(STR_SETTINGS_TITLE);
renderer.drawText(font, x, y, tr(STR_BROWSE_FILES));
LOG_INF("I18N", "Status: %s", tr(STR_CONNECTED));

// I18N - Shorthand for I18n::getInstance()
I18N.setLanguage(Language::ES);
Language lang = I18N.getLanguage();

// === Full API ===

// Get the singleton instance
I18n& instance = I18n::getInstance();

// Get translated string (three equivalent ways)
const char* text = tr(STR_SETTINGS_TITLE);              // Macro (recommended)
const char* text = I18N.get(StrId::STR_SETTINGS_TITLE);   // Direct call
const char* text = I18N[StrId::STR_SETTINGS_TITLE];       // Operator overload

// Set runtime language
I18N.setLanguage(Language::ES);

// Get current language
Language lang = I18N.getLanguage();

// Get character set for font subsetting (static method)
const char* chars = I18n::getCharacterSet(Language::FR);

// Persist a user language choice
SETTINGS.language = static_cast<uint8_t>(Language::ES);
SETTINGS.saveToFile();
```

## File Storage

The selected language is stored with the rest of the device settings in:
```text
/.crosspoint/settings.json
```

The JSON field is `language`, stored as a stable language code string such as
`"EN"`, `"DE"`, or `"HE"` rather than a raw enum value.

Older firmware versions used:
```text
/.crosspoint/language.bin
```

That legacy file is no longer read. Upgrading from a firmware old enough to
have written it resets the language to the default; re-select it once and it
persists in `settings.json`.

## Translation Workflow

### For Developers (Adding Features)

1. Add new strings to `lib/I18n/translations/english.yaml`
2. Run `python3 scripts/gen_i18n.py lib/I18n/translations lib/I18n/`
3. Use the new `StrId` in your code
4. Request translations from translators

### For Translators

1. Open the YAML file for your language in `lib/I18n/translations/`
2. Add or update translations using the format `STR_KEY: "translated text"`
3. Keep translations concise (E-ink space constraints)
4. Make sure the file is in UTF-8 encoding
5. Run `python3 scripts/gen_i18n.py lib/I18n/translations lib/I18n/` to verify
6. Test on device or submit for review
